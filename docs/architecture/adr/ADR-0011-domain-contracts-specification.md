# ADR-0011: Domain Contracts Specification

## Status

Accepted

---

## Context

Ziva Latam has a defined architecture composed of independent modules:

- Identity Service
- Evidence Service
- Trust Engine
- API Gateway
- Orchestration Layer

However, without strict domain contracts:

- modules may interpret data differently
- trust logic may become inconsistent
- integration boundaries may break
- future implementation may drift from architecture

A unified contract system is required.

---

## Decision

Ziva Latam will define **system-wide Domain Contracts** that all modules MUST respect.

These contracts define:

- data structures
- input/output formats
- event schemas
- badge definitions
- trust profile structure

---

## Core Principle

> All modules communicate through contracts, never through assumptions.

---

# Core Domain Contracts

## 1. Evidence Contract

Represents any financial input submitted by a user.

```typescript
type EvidenceType =
  | "income"
  | "payment"
  | "purchase"
  | "contract"
  | "identity_document";

interface Evidence {
  evidenceId: string;
  userId: string; // internal UUID only
  type: EvidenceType;
  source: "manual" | "upload" | "integration";
  timestamp: string;

  data: {
    amount?: number;
    currency?: string;
    description?: string;
    issuer?: string;
    metadata?: Record<string, unknown>;
  };

  verificationStatus: "pending" | "validated" | "rejected";
}
```

---

## 2. Badge Contract

Represents a trust signal generated by the Trust Engine.

```typescript
type BadgeType =
  | "Identity Verified"
  | "Income Verified"
  | "Stable Income"
  | "Consistent Payments"
  | "Active Financial History"
  | "Low Documentation Risk"
  | "High Evidence Coverage";

interface Badge {
  badgeId: string;
  userId: string;
  type: BadgeType;

  status: "active" | "revoked" | "pending";

  evidenceReferences: string[];

  generatedAt: string;
  lastUpdatedAt: string;

  explanation: {
    reason: string;
    triggeringRules: string[];
  };
}
```

---

## 3. Financial Trust Profile (FTP)

Represents the final output consumed by B2B systems.

```typescript
interface FinancialTrustProfile {
  userId: string;

  badges: Badge[];

  trustSignals: {
    incomeStability: "low" | "medium" | "high";
    paymentReliability: "low" | "medium" | "high";
    documentationStrength: "low" | "medium" | "high";
  };

  verificationStatus: {
    identity: boolean;
    income: boolean;
    evidenceCoverage: "none" | "partial" | "complete";
  };

  generatedAt: string;
}
```

---

## 4. Trust Event Contract

Used internally for orchestration between services.

```typescript
interface TrustEvent {
  eventId: string;
  type: "EVIDENCE_SUBMITTED" | "EVIDENCE_VALIDATED" | "BADGE_GENERATED";

  userId: string;
  payload: Record<string, unknown>;

  timestamp: string;
}
```

---

## Contract Rules

### 1. No Module-Specific Extensions

Modules cannot modify core contracts.

---

### 2. Versioning Required

Any change to contracts must:

- increment version
- create ADR reference
- preserve backward compatibility where possible

---

### 3. Strict Typing Enforcement

All implementations must strictly adhere to contracts.

No partial or inferred structures allowed.

---

### 4. No Cross-Domain Leakage

- Evidence structures cannot contain identity data
- Badges cannot expose raw evidence
- FTP cannot expose internal system IDs

---

## Alternatives Considered

### 1. Flexible Schema per Module

Rejected because:

- leads to inconsistency between services
- increases integration risk
- breaks system predictability

---

### 2. No Formal Contracts

Rejected because:

- guarantees architectural drift
- makes system unmaintainable
- breaks long-term scalability

---

### 3. Database-Coupled Contracts

Rejected because:

- couples system to storage layer
- reduces architectural flexibility
- increases migration cost

---

## Consequences

### Positive

- strict consistency across modules
- predictable system behavior
- easier debugging and auditing
- strong foundation for API design
- clear implementation contracts for developers

---

### Negative

- reduced flexibility for ad-hoc changes
- requires strict governance
- increases initial development discipline
- slower prototyping speed

---

## Impact on System

This ADR defines:

- internal communication schema
- data structures for all core modules
- foundation for implementation layer (MXL)
- strict boundaries between services
- basis for API contract stability

---

## Core Principle

> If it is not in the contract, it does not exist in the system.

---

Accepted
